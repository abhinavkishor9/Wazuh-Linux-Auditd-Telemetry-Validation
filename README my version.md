# Wazuh-Linux-Auditd-Telemetry-Validation
## Overview
### 1. What is Linux Auditd?

Linux Audit is a security auditing framework that records system-level activities for monitoring, investigation, and compliance purposes.

The `auditd` daemon collects audit events generated by the Linux kernel and writes them to the configured audit log.

The default audit log location on Rocky Linux is:

```text
/var/log/audit/audit.log
```

Audit telemetry can provide information about:

- User authentication activity.
- Account and privilege changes.
- File and directory access.
- Configuration modifications.
- System call execution.
- Process execution.
- Changes to security-sensitive files.
- Kernel module loading attempts.

For SOC analysts, these records provide valuable evidence about who performed an operation, what happened, when it occurred, and whether it succeeded.

### 2. How Linux Audit Events Work

Linux Audit records events using different record types.

Some important audit record types include:

| Audit Record | Purpose |
|---|---|
| SYSCALL | Records system call activity |
| PATH | Identifies files involved in an audited operation |
| CWD | Records the current working directory |
| EXECVE | Records command execution arguments |
| USER_AUTH | Authentication-related activity |
| USER_LOGIN | Login-related activity |
| USER_CMD | User command activity |
| CONFIG_CHANGE | Audit configuration changes |
| AVC | SELinux access-control decisions |

A single audit event can contain multiple records sharing the same audit event ID.

For example, a file access operation may generate SYSCALL, CWD, and PATH records. These records should be correlated rather than treated as unrelated events.

### 3. Understanding Audit Rules

Audit rules determine which activities should be monitored.

Rules can monitor:

- Specific system calls.
- File access.
- File modifications.
- User activity.
- Privileged operations.
- Changes to audit configuration.

Example:

```bash
auditctl -w /etc/passwd -p wa -k account_changes
```

Explanation:

- `-w` specifies the file or directory to monitor.
- `-p wa` monitors write and attribute changes.
- `-k` assigns a searchable key to the rule.

The key helps analysts retrieve matching events using `ausearch`.

Example:

```bash
ausearch -k account_changes -i
```

**Important:** Audit rules can be runtime rules or persistent rules. Runtime rules may disappear after reboot. This lab initially uses runtime rules to avoid making unnecessary permanent configuration changes.

### 4. How Wazuh Collects Auditd Telemetry

Wazuh can collect Linux Audit records from the audit log.

The general event pipeline is:

```text
System Activity
      |
      v
Linux Kernel Audit Subsystem
      |
      v
auditd
      |
      v
/var/log/audit/audit.log
      |
      v
Wazuh Log Collection
      |
      v
Wazuh Decoder
      |
      v
Wazuh Rules
      |
      v
Wazuh Alerts
      |
      v
Wazuh Dashboard
```

Each stage has a different responsibility:

1. Linux Audit generates records for monitored activity.
2. `auditd` receives and stores audit records.
3. Wazuh collects the configured audit log.
4. Wazuh decodes the collected records.
5. Wazuh rules evaluate the decoded information.
6. Matching events are presented as alerts when the applicable rules generate alerts.

An audit record may exist without producing a Wazuh alert. This can happen because of collection configuration, decoder behavior, rule matching, or alert-generation settings.

### 5. Why Telemetry Validation Matters

A SIEM is only useful when the required security events reach it correctly.

For example:

- An audit rule may be configured but never generate an event.
- `auditd` may be active but not monitoring the intended activity.
- Audit records may be written locally but not collected by Wazuh.
- Wazuh may receive records but fail to decode or match them.
- A decoded event may not produce an alert because no applicable rule generates one.

Therefore, analysts should validate the complete telemetry pipeline instead of assuming that an active service means successful monitoring.

### 6. What Should Be Validated?

| Validation Stage | What to Verify |
|---|---|
| Audit service | `auditd` is active |
| Audit configuration | Expected rules are installed |
| Event generation | Controlled activity produces audit records |
| Local storage | Records appear in `audit.log` |
| Event retrieval | `ausearch` retrieves the expected events |
| Wazuh collection | Wazuh is configured to read the audit log |
| Decoding | Audit records are interpreted correctly |
| Rule matching | Relevant Wazuh rules are triggered |
| Alert visibility | Events appear in the Wazuh Dashboard |

This lab validates Linux Auditd telemetry generation and its collection by Wazuh.

The investigation follows controlled file activity on a Rocky Linux system and examines how Linux Audit records the activity, how the records are stored locally, and how Wazuh processes audit telemetry.

The objective is to validate the different stages of the telemetry pipeline rather than assume that an active audit service automatically guarantees successful SIEM monitoring.

## Lab Objectives – Linux Auditd Telemetry Validation Using Wazuh

### Primary Objective

Validate the generation and collection of Linux Audit telemetry and examine how Wazuh processes audit records generated by controlled system activity.

### Technical Objectives

1. **Audit Service Verification**
   - Inspect the Linux Audit service.
   - Confirm whether auditing is enabled.
   - Review the current audit status and loaded rules.

2. **Audit Rule Configuration**
   - Create a dedicated directory for controlled testing.
   - Configure a runtime audit watch rule.
   - Understand write and attribute-change monitoring.
   - Verify the installed rule using `auditctl`.

3. **Controlled Event Generation**
   - Generate file creation activity.
   - Perform a controlled file write.
   - Modify file permissions.
   - Observe how these operations are represented in Linux Audit.

4. **Audit Record Investigation**
   - Retrieve events using `ausearch`.
   - Identify the relevant audit event IDs.
   - Examine SYSCALL, PATH, CWD, and PROCTITLE records.
   - Identify the process, executable, user, file path, syscall, and operation result.

5. **Wazuh Telemetry Validation**
   - Inspect the Wazuh audit log collection configuration.
   - Verify the Wazuh Manager and log collector status.
   - Review the Wazuh Discover event.
   - Identify the applicable rule ID, rule level, description, and event source.

6. **Event Correlation**
   - Correlate local audit records with Wazuh events.
   - Differentiate audit configuration changes from monitored file activity.
   - Determine which telemetry stages are confirmed and which remain unverified.

7. **Cleanup and Documentation**
   - Remove the controlled test files and directory.
   - Verify the status of the temporary audit rule.
   - Record any cleanup failures.
   - Document findings without assuming that an unverified operation succeeded.

### Learning Outcomes

By completing this lab, the analyst should be able to:

- Explain how Linux Audit generates security telemetry.
- Configure and verify a runtime audit watch rule.
- Investigate file activity using Linux Audit records.
- Interpret related audit record types.
- Understand Wazuh audit log collection configuration.
- Analyze audit configuration-change alerts.
- Distinguish local event generation from SIEM alert generation.
- Identify telemetry gaps and document evidence-based conclusions.

## Lab Scenario

### Scenario

A SOC analyst is validating Linux security telemetry on a Rocky Linux 9.8 system monitored by Wazuh.

The objective is to determine whether Linux Audit can capture controlled file activity and whether the resulting records are available for SIEM investigation.

Although the audit service is running, the initial audit rule inspection returns no loaded rules. The analyst therefore needs to establish a controlled monitoring configuration and generate test activity without modifying important operating system files.

### Investigation Approach

The analyst creates a dedicated directory under `/var/tmp` and configures a runtime audit watch rule to monitor write and attribute changes.

Controlled operations are then performed against a test file:

- File creation using `touch`.
- File content modification using shell redirection.
- Permission modification using `chmod`.

The analyst retrieves matching audit records and examines the associated process, executable, syscall, file path, user identity, and operation result.

The investigation then moves to Wazuh. The analyst inspects the manager configuration to determine whether `/var/log/audit/audit.log` is configured for collection and reviews the Discover event generated during the audit rule configuration.

### Investigation Challenge

The Wazuh Dashboard displays an audit configuration-change alert after the runtime rule is added.

The analyst must determine what this alert actually represents.

The alert identifies the audit rule addition operation. It should not automatically be interpreted as an alert for the file creation, write, or permission modification that followed.

The local audit records and Wazuh alert must therefore be examined as separate pieces of evidence.

### Expected Investigation Questions

- Was the audit service active and enabled?
- Was auditing enabled at the kernel audit subsystem level?
- Was the runtime watch rule successfully installed?
- Did the controlled file operations generate local audit records?
- Which processes and system calls were associated with the operations?
- Was Wazuh configured to collect the audit log?
- What activity triggered the Wazuh configuration-change alert?
- Were separate Wazuh alerts for the file operations established?
- Was the temporary audit rule successfully removed during cleanup?

### Investigation Outcome

The controlled file operations generated local audit records, and the Wazuh configuration contained an audit log collection entry.

Wazuh also processed an audit configuration-change event associated with adding the runtime rule.

However, the available Dashboard evidence did not establish separate Wazuh alerts for the controlled file operations. The attempted audit rule removal also failed, although the test directory was deleted.

The scenario demonstrates why SOC analysts must validate telemetry generation, collection, processing, alert matching, and cleanup independently rather than treating one successful stage as proof of the entire monitoring pipeline.

## Audit Monitoring Configuration

A runtime watch rule was configured for a dedicated test directory.

```bash
auditctl -w /var/tmp/lab132 -p wa -k lab132_file_activity
```

The rule monitored write and attribute changes and assigned the key `lab132_file_activity`.

The loaded rule was verified using:

```bash
auditctl -l
```

## Controlled Activity

The following operations were performed:

```bash
mkdir -p /var/tmp/lab132

touch /var/tmp/lab132/audit-test.txt

echo "Lab 132 Auditd Telemetry Validation" > /var/tmp/lab132/audit-test.txt

chmod 600 /var/tmp/lab132/audit-test.txt
```

The operations generated audit records associated with the configured key.

## Local Audit Validation

Matching records were retrieved using:

```bash
ausearch -k lab132_file_activity -i
```

The investigation identified records for:

- Audit rule configuration.
- File creation using `touch`.
- File writing through a shell operation.
- File permission modification using `chmod`.

The records contained process information, file paths, syscall details, user identity, and operation results.

## Wazuh Collection Configuration

The Wazuh configuration contained the following local file collection entry:

```xml
<localfile>
  <log_format>audit</log_format>
  <location>/var/log/audit/audit.log</location>
</localfile>
```

This confirmed that Wazuh was configured to collect the Linux Audit log using the audit format.

The Wazuh Manager was active, and its log collector process was running.

## Wazuh Alert Analysis

The Wazuh Discover event showed:

| Field | Observed Value |
|---|---|
| Rule ID | 80705 |
| Rule Level | 3 |
| Rule Description | Auditd: Configuration changed. |
| Rule Groups | audit, audit_configuration |
| Input Type | log |
| Location | /var/log/audit/audit.log |
| Manager | localhost.localdomain |
| Event Time | Nov 9, 2026 @ 07:43:32.111 |

The underlying audit event was associated with the addition of the `lab132_file_activity` rule through `auditctl`.

The alert therefore demonstrated Wazuh processing of an audit configuration-change event. It was not evidence that separate alerts were generated for the subsequent file creation, write, and permission-change operations.

## Key Findings

- The Linux Audit service was active and enabled.
- Audit was enabled, and the initial audit rule list was empty.
- The initial audit status showed zero lost records.
- A runtime watch rule was successfully installed for `/var/tmp/lab132`.
- Linux Audit recorded the controlled file operations.
- The `ausearch` output included successful `openat` and `fchmodat` operations.
- Wazuh was configured to collect `/var/log/audit/audit.log`.
- The Wazuh Manager and log collector were running.
- Wazuh generated alert `80705` for the audit configuration change.
- Separate Wazuh alerts for the controlled file operations were not established by the supplied screenshot.

## Troubleshooting and Cleanup

The audit watch command returned the warning:

```text
Old style watch rules are slower
```

The rule was nevertheless installed and appeared in `auditctl -l`.

During cleanup, the attempted rule removal failed with:

```text
Error sending delete rule data request (No such file or directory)
There was an error while processing parameters
```

The subsequent `auditctl -l` output still showed the watch rule.

The test directory was deleted successfully, but removal of the runtime audit rule was not confirmed.
